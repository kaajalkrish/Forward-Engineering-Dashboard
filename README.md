# Forward Engineering Dashboard

A progress dashboard for the COBOL → Java/Spring Boot forward-engineering harness. It
shows one workspace end to end: four phase cards (Understand → Design →
Migrate → Implementation, where Implementation lists the user stories), all 13 journey stages and their gates, the epic/story backlog and how each story
is being built, and the traceability from COBOL paragraphs to generated Java and tests.

It is separate from the harness's own `web/` cockpit: the cockpit *drives* the harness stage
by stage; this dashboard *reports* on it. The harness itself lives in its own repository and
is not included here; this repo contains only the dashboard.

## Run it

Needs Node.js 18+ only.

```bash
cd dashboard
npm install      # first time only
npm run dev      # → http://localhost:8788
npm run build    # typecheck + production build into dist/
```

Useful links:

- `http://localhost:8788/#build`: open a tab directly (every tab has a `#key`)
- `http://localhost:8788/?story=US-FR-5#build`: open with a story's detail panel showing
- `http://localhost:8788/?data=sample`: the illustrative sample instead of the imported output
- `http://localhost:8788/?demo=1#build`: start the implementation demo straight away

### Implementation demo

The **Run implementation demo** button simulates the Build stage: each story goes through the
harness's 8-step loop (context pack → tests → RED → implementation → GREEN → repair → quality gate
→ record status) in plan order, and the KPIs, sidebar, Build tab, story panels and timeline update
live. One story in five needs a repair pass so that step is visible. Everything it shows is
labelled **Demo · simulated**; nothing is run or saved, and **Back to real data** restores the
imported view (`src/lib/useBuildDemo.ts`).

## Where the data comes from

The page reads **one file**, re-fetched every 30 seconds (the "Live · updated" chip):

| File | What it is |
|---|---|
| `public/data/dashboard-data.json` | **Real output**, generated by `npm run import` (git-ignored, run-specific) |
| `public/data/sample.json` | Illustrative sample. Shown with `?data=sample`, or automatically when no import exists |

A banner at the top always says which one you are looking at, what is real, and what the
imported output does not contain.

### Importing real harness output

```bash
npm run import -- --harness <path to the harness checkout>   # finds <harness>/codegen_output/…
node scripts/import-codegen.mjs <module-folder>                # or point at a module explicitly
```

`scripts/import-codegen.mjs` reads the generated Maven module (the folder with `pom.xml`)
and writes `dashboard-data.json`. It uses **only what is in the files**:

- stories, acceptance-criteria IDs and COBOL lineage (test-file headers and the
  `Story codegen trace` blocks story_runner.py prepends; their order gives the build order)
- services, REST endpoints and JPA entities (the `TODO(story:… service:…)` markers and annotations)
- test analysis: package validity, placeholder assertions, COBOL behaviour referenced,
  compile problems recorded in `target/` class files
- code findings (with the harness source location when the cause is in the harness)

Fixed facts about the harness (phases, 13 stages, 16 gates, 11 agent roles, build loop) come
from `scripts/harness-model.json`, taken from the harness code. Anything the module cannot tell
us (BRD and judge scores, gate results and approvals, costs, timeline, seams, domain design)
is left empty and the tab says what source would fill it. Story statuses are **derived** from
the files and labelled as such; stage statuses before Build are **inferred** (Build needs them)
and labelled as such.

### How each section maps to the harness

| JSON section | Harness source |
|---|---|
| `phases`, `stages`, `gates` | `controlplane/stages.py`, gate upserts in `controlplane/*.py`; Postgres `journey_stage`, `gate`, `approval` |
| `agentRoles` | `cost/tiering.py` (11 roles, Haiku / Sonnet / Opus) |
| `buildSteps`, `stories[].codegen` | `codegen/story_runner.py`, `codegen/story_quality.py`; artifact `story_codegen_status` |
| `epics`, `stories` | `backlog/schema.py` (Epic, UserStory, AcceptanceCriterion) |
| `seams` | seam candidates from `queries.py` (weighted score) |
| `contexts`, `services` | `domain/schema.py`, `technical_design/schema.py` |
| `artifacts` | Postgres `artifact` (kind + version) |
| `workUnits`, `timeline` | Postgres `work_unit`, `agent_run_event` |
| `failures` | Postgres `defect_ticket` + failed work units / stories |
| `quality.build` | `codegen/quality_gate.py` (`mvn verify` gates) |
| `quality.brdJudge` | `agent/brd_judge.py` (five weighted dimensions, rated high at ≥ 4.2) |
| `state` | Postgres `agent_run`, `budget` |
| `code` | static analysis of `codegen_output/<module>` |

## Layout

```
src/
  types.ts                 data contract
  lib/                     loader, metrics, story helpers, date formatting
  components/              shell: sidebar, header, KPI tiles, tab bar, story drawer, charts, ui
  tabs/registry.ts         tab groups, labels and headings
  tabs/overview/           Pipeline, Traceability, Quality & Coverage, Gates & Approvals
  tabs/delivery/           Backlog, Story Plan, Build, Generated Code, Artifacts, Work Units
  tabs/architecture/       Seams, Domain Design, Services, Tech Stack
  tabs/agents/             Agent Roles, Build Loop
  tabs/activity/           Timeline, Graphs, Feedback, Failures, Ask
  tabs/system/             Inputs, State
```

Stack: React 19, TypeScript, Vite, Tailwind CSS, lucide-react icons. Charts are plain SVG
(no chart library). **Export PDF** uses the browser's print dialog (print styles hide the
controls and keep cards whole); **JSON** downloads the current data file.
